# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없는 항목에만 적용한다.

## 적용 기준

### TDD를 반드시 적용한다

- **비즈니스 로직**
- **API** (엔드포인트, 핸들러, 외부 서비스 호출 래퍼)
- **유틸 함수**
- **버그 수정** (재현 테스트를 먼저 작성한다)

### TDD가 불필요하다

- **타입 정의**
- **설정 파일**
- **순수 UI** (스타일, 레이아웃, 정적 마크업)
- **SQL** (스키마, 마이그레이션)

경계가 모호하면 **적용하는 쪽**으로 판단한다.

## RED-GREEN-REFACTOR

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고친다.

### 2. GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 사이클을 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다. 삭제한 코드를 보면서 테스트를 맞추면 테스트가 구현에 종속된다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 30초면 쓴다. 단순한 코드가 깨질 때 가장 늦게 발견된다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현을 그대로 따라 쓰게 되어 버그를 잡지 못한다. 그리고 나중은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓴다. 시간이 없을수록 사이클이 필요하다. |
| 삭제하면 낭비다 | 이미 쓴 시간은 매몰 비용이다. 검증 안 된 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| 프로토타입이다 | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트도 버리면 되지만, 남길 코드라면 처음부터 테스트가 있어야 한다. |
