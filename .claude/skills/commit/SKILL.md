# Commit

변경사항을 분석하고 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다. 별도의 사용자 승인 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경 파일(추적/미추적)을 확인한다. git 저장소가 아니면 이유를 알리고 중단한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 내용을 읽는다.
- `git log --oneline -10`으로 기존 커밋 메시지 스타일을 참고한다.
- `.env`, 키·토큰, `node_modules` 등 커밋하면 안 되는 파일이 섞여 있으면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적(기능 추가와 리팩터링, 버그 수정과 설정 변경 등)이 섞여 있으면 나눈다.
- 각 단위에 포함할 파일을 정한다. 한 파일에 여러 목적의 변경이 섞여 있으면 사용자에게 어떻게 나눌지 묻는다.
- 변경이 하나의 목적이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성
형식: `<type>: <요약>`

| type | 용도 |
| --- | --- |
| feat | 사용자에게 보이는 기능 추가·변경 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드, 설정, 의존성, 문서 등 기타 |

규칙:
- 요약은 한국어, 50자 안팎, 마침표 없이 "무엇을 했는지"를 쓴다. (예: `feat: 프롬프트 입력창에 Ctrl+Enter 전송 추가`)
- 이유나 배경이 필요하면 한 줄 띄우고 본문에 쓴다.
- 마지막에 빈 줄을 두고 시스템 안내에 있는 공동 작성자 줄을 붙인다. (예: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`)

### 4. 커밋
- 사용자 승인을 기다리지 않고 단위별로 `git add <파일>` → `git commit`을 바로 실행한다. `git add -A`나 `git add .`는 쓰지 않고 파일을 명시한다.
- 여러 줄 메시지는 heredoc으로 전달한다.
- 끝나면 `git log --oneline`으로 단위별 포함 파일과 메시지를 요약해 보여준다.

## 하지 않는 것
- push, amend, force 옵션, hook 우회(`--no-verify`)는 사용자가 명시적으로 요청하지 않으면 하지 않는다.
- pre-commit hook이 실패하면 원인을 고치고 새 커밋을 만든다.
